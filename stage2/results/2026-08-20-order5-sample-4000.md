# 2026-08-20: 4,000-row generated sample of order-5 equation pairs (<=3 variables)

Goal: push testing into order-5 (term-size 5) equations, the space
`evaluation_order5` is drawn from. Unlike order-4, **there is no precomputed
implication matrix for order 5** (that would be ~62,576^2 pairs and has never
been computed by anyone) - the pairs had to be generated, not sampled from a
graph. Measurement + logging only, per explicit instruction; no solver
changes, fixes deferred to a later "improvement pass" session.

## Method

- `stage2/experiments/sample_order5_pairs.py` (new): draws random distinct
  pairs from `vendor/stage2-official/examples/problems/eq_size5.txt` (62,576
  laws, `*` notation - the same catalog `evaluation_order5` is drawn from),
  filtered to equations with **at most 3 variables** each (26,990 of the
  62,576 qualify). No labels are attached - there is no ground truth to
  attach.
- `audit_corpus.py`'s `--file` path handles a missing `answer` field already
  (it just skips the ground-truth cross-check line in `audit_row` and does
  full offline-oracle verification regardless). **This means "oracle
  failures: 0" here is self-consistency evidence (every claimed verdict is
  independently proof-kernel/model-check/witness-verified sound), not
  verified-correct-against-known-truth evidence** - there is no known truth
  for arbitrary order-5 pairs to check against. Do not conflate the two when
  citing this number.
- Sample: seed `20260820`, 10,000 pairs generated
  (`stage2/results/order5-sample-10000-2026-08-20.jsonl`), audited in a
  4,000-row slice (`order5-sample-4000-2026-08-20.jsonl`) after a 200-row
  pilot and a scope-reduction request (10,000 unbounded projected to ~2.5-3h;
  4,000 at a 300s row-budget was the chosen scale).
- `audit_corpus.py` was extended mid-session to print progress every 100
  rows even in multi-worker mode (previously silent until the entire sweep
  finished, which made a slow-but-healthy run indistinguishable from a hung
  one - see the timing note below).
- Audited at `fast` effort, `--row-budget 300` (order-4 needed no cap; a
  200-row order-5 pilot showed a much heavier skip-row tail - 6/200 skips at
  ~450-550s unbounded each vs the slowest genuine solve at 203s - so a cap
  was applied here from the start, unlike the order-4 runs).

## Results

| | Value |
| --- | --- |
| Rows | 4,000 |
| Solved | 3,795 (94.9%) |
| Skipped | 205 (5.1%) |
| Crashes | 0 |
| Oracle failures | 0 |
| Solver-claimed TRUE / FALSE (no ground truth to check against) | 718 / 3,077 |
| Wall clock (16 workers) | 5,865 s (~98 min) |

0 crashes and 0 oracle failures across 3,795 solved rows: every TRUE
certificate proof-kernel-verified or model-checked, every FALSE witness table
independently re-verified, self-consistently sound. The heavy skew toward
FALSE (3,077 vs 718) is expected - most random pairs of unrelated order-5 laws
are not implications, so the countermodel search is doing most of the work,
same shape as the order-4 pilot before it was balanced by construction (order-4
sampling forced 50/50 off a known matrix; this generator cannot know the split
in advance since nothing is labelled).

## Timing bug found: a 300s row-budget is not always a 300s row-budget

9 of the 205 skip rows overran the nominal 300s cap, from ~315s up to
**3,538s on `order5_23416_48258`** (eq1 `x = ((y * x) * z) * (y * (z * z))`,
eq2 `x * y = (z * (y * x)) * (z * x)`) - an ~11.8x overshoot. This is the same
bug shape already on record three times in `CLAUDE.md` (rails 5f-iv, 5f-v,
5f-vi): some engine path polls the deadline once per outer iteration rather
than per unit of work, and a big-enough inner search runs straight through
its budget. It was invisible until now because nothing had previously
exercised order-5-shaped terms (larger, more distinct subterms) through
whichever engine this is. **Flagging for the improvement pass, not diagnosing
further this session** - the fix pattern is already known (mirror the
poll-frequency fix from 5f-v/vi into whichever engine's inner loop this is;
`faulthandler.dump_traceback_later` on a standalone repro of
`order5_23416_48258` will name it directly, per rail 5f-vi's own method,
rather than guessing from the route name).

This bug is also the full explanation for the session's earlier timing
confusion (a 4,000-row run that "should" take ~50-60 min by naive scaling
took ~98 min, and an initial background run looked stalled for long stretches
with zero visibility before progress-logging was added): a handful of rows
silently eating 5-12x their allotted budget, invisible without per-row
progress output, is exactly enough to produce that symptom without anything
being deadlocked.

## The failure frontier is diffuse, unlike order-4's

Order-4's 23-row failure frontier was **one single law family** (every eq1
shaped `x = F(x,y,z)`, `term_size(F)=4`). Order-5's 205-row frontier does
**not** show that pattern: the most-repeated eq1 id appears only 3 times
(`37581`), and the next tier repeats only twice - no small set of hypothesis
laws dominates the way `2920`/`1923`/`944`/`1350` did for order-4. 204/205
frontier eq1s use exactly 3 variables (expected - that's the max this sample
allows) and eq2 splits 166/37/2 across 3/2/1 variables. Read this as: order-5
misses are spread across many distinct hard instances rather than one
recognizable, generalizable shape - a real difference from the order-4
finding, not a restatement of it.

## Not done this session (per instruction)

- **No LLM lemma-lane pass on the 205-row frontier.** Order-4's entire miss
  set was TRUE-labeled, so a single clear next step (try lemma proposals)
  made sense. Order-5 has no ground truth, so some of these 205 "skip"
  rows could be solver-correct-but-unproven FALSE rows for which no LLM
  lemma attempt would ever apply - running the lemma lane blind here isn't
  the obviously correct move the way it was for order-4, so it was withheld
  pending a decision on how to handle the no-ground-truth case.
- **No fix for the row-budget overshoot bug.**
