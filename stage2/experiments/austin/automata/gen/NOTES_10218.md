**`ROOT` is the W3-7 general invariant for this law** and covers the two dominant cells (R1 and R5,
1,577,332 of 1,577,776 assignments).  Its proof is `by_cases hf : op x y = J x y`:

* `op x y` free -> `P1` holds with **seven `rfl`s** and the value `a1 (a1 v)` is `x` by `rfl`;
* `op x y` decoded -> `Dv` gives `sz (op x y) < sz y`, hence `y ≠ a2 (op x y)`, and that single
  disequality **kills rules 1-4 at once** (they share the conjunct `u = a2 (a1 v)`); rule 5 then
  fires with an `rfl` guard, because its `p3` is literally `op x y` — the chain's own first product.

Gate note (cost two compiles): state the gate in the **unreduced** form that `op_cases` uses
(`msr (a2 (a1 (a2 (J (op x y) (J (J z x) y))))) y < …`) or `rw [dif_pos g3] at hp3` fails with
"Did not find an occurrence of the pattern" — `PLAYBOOK_PROOF.md` §7 pitfall 4, in the other
direction.  Prove it with `simp only [a1_J_eq, a2_J_eq]; exact msr_lt_of_max_lt (mxl _ _)`;
plain `omega` cannot do the max-vs-max goal (`LEMMA_LIBRARY.md`, `mxl`).

## Exactly what is left

`theorem law (x y z : M) : op y (op (op x y) (op (op z x) y)) = x`.  Two obligations:

1. **`t4` free**: `op t1 t3 = J t1 t3`.  Via `Wne` this is `t1 ≠ a2 (a1 t3)` and `t1 ≠ a2 (a2 t3)`.
   With `t2, t3` free that reads `op x y ≠ x` and `op x y ≠ a2 y`.  **Both hold whenever `op x y` is
   free** (size), and when `op x y` is decoded `Dv` gives `sz (op x y) < sz y`, which kills
   `op x y = a2 y`?  No — it does not; `sz (a2 y) < sz y` too.  This is the one open leaf.  The extra
   fact available is `TRs`: a decoded `op x y` is `a1 (a1 y)`, `a2 (a1 (a2 y))` or `a2 (a1 x)`;
   the third has `sz < sz x` and so cannot equal `x`.  A `CMP`-style shape invariant
   (`PLAYBOOK_PROOF.md` §4) on decoded values is the tool if size alone will not separate them.
2. **The four minor cells** (R2/R3/R4/R6, 444 of 1,577,776 assignments), i.e. `t2` or `t3` decoded.
   Each is one rule lemma of the same shape as `ROOT`'s second half: the shared conjunct
   `u = a2 (a1 v)` (rules 1-4) or `u = a2 (a2 v)` (rules 5-6) is either `rfl` or refuted by `Dv`,
   and the surviving rule's guard is `rfl` because its `p_k` is a chain product.  R2's guard is
   `t2 = op (a2 (a1 x)) x`, which is `rfl` exactly when `t2` decoded by rules 1-4 (`z = a2 (a1 x)`);
   the `z = a2 (a2 x)` case is served by R4/R6 — `gen/_x10218_cell.py` builds it and the law holds.

## THE METHODOLOGICAL POINT (this is the part to carry to other laws)

My **first** forced-firing run (`gen/_x10218_force.py`) reported **3,846 assignments, 0 failures** and
was **vacuous**.  The cell census printed beside it is what exposed it:

```
force-t1-R2   ('R1', 'F', 'F', 'F', 'R5')   768      <- R1 fired, not R2
force-t1-R3   ('R1', 'F', 'F', 'F', 'R5')   256      <- R1 fired, not R3
force-t1-R6   ('R1', 'F', 'F', 'F', 'R5')    64      <- R1 fired, not R6
```

**Why:** rules R2..R6 differ from R1 only in that a product inside their guard is *decoded* rather
than free.  Build that product free and R1's precondition holds too, R1 is checked first, and the
"forced" firing never happens.  The fix is mechanical and transfers to every law of this family:

> To force rule k, build the product inside rule k's own guard as an **encoding**, so that it decodes.

Corrected constructors (`gen/_x10218_force2.py`), with `enc(P,u,Q) = J (J P u) (J (J Q P) u)`:

| R3 | `u := enc(Wt, J A2 P, Q)` (so `op (a2 (a1 u)) u = Wt`); `v := J (J P u) Wt` | fires R3 |
| R5 | `u := enc(D,P,Q)` (so `op P u = D`); `v := J D (J (J Q P) u)` | fires R5 |
